## 2. 数据模型

### 2.1 核心表

```sql
-- 用户与账户
users(id, name, phone, id_card_masked, created_at)
accounts(id, user_id, type, balance_cents, available_cents, currency, card_no_mask)
  -- type: savings|deposit|credit
  -- available_cents = balance - held，冻结金额不计入可用

cards(id, user_id, account_id, card_no_mask, kind, status, daily_limit_cents)
  -- kind: debit|virtual|credit ; status: active|frozen|cancelled

contacts(id, user_id, name, phone, memo, relation, last_used_at, use_count)
  -- memo/relation 用于「给我妈转钱」这类口语解析
  -- last_used_at + use_count 用于判定「新收款人」

transactions(id, user_id, account_id, direction, amount_cents, counterparty,
             memo, category, sub_category, occurred_at, source)
  -- category: 餐饮|交通|购物|娱乐|居住|医疗|教育|转账|理财|订阅|其他

subscriptions(id, user_id, merchant, amount_cents, period, next_charge_at,
              status, detected_from_txn_id)
  -- status: active|cancelled|paused

wealth_products(id, name, kind, risk_level, expected_annual_pct,
                min_amount_cents, term_days, issuer)
wealth_positions(id, user_id, product_id, amount_cents, purchased_at, status)
```

### 2.2 资金两阶段提交表

```sql
holds(id, user_id, account_id, tool, params_hash, amount_cents,
      status, idempotency_key, created_at, expires_at, committed_at)
  -- status: held|committed|released|expired
  -- ★ 唯一约束 (idempotency_key) 保证重试不重复扣款
```

### 2.3 任务与决策链

```sql
tasks(id, user_id, session_id, goal_text, plan_json, status, created_at)
  -- status: planning|running|paused|awaiting_confirm|awaiting_factor|
  --         completed|failed|cancelled|escalated
task_nodes(id, task_id, node_key, tool, params_json, status,
           depends_on_json, receipt_json, decision_json, error,
           started_at, finished_at)
  -- status: pending|ready|running|done|failed|skipped|rolled_back

sessions(id, user_id, channel, trust_level, created_at, last_active_at)
messages(id, session_id, role, content, envelope_json, created_at)
```

### 2.4 安全相关

```sql
audit_log(
  seq INTEGER PRIMARY KEY AUTOINCREMENT,
  ts TEXT NOT NULL,
  session_id TEXT, task_id TEXT,
  event_type TEXT NOT NULL,   -- user_msg|intent|plan|policy|factor|tool_call|receipt|denial
  payload_json TEXT NOT NULL,
  prev_hash TEXT NOT NULL,    -- ★ 前一条的 hash
  hash TEXT NOT NULL          -- ★ sha256(prev_hash + ts + event_type + payload_json)
)
-- 只允许 INSERT，DB 层用触发器禁止 UPDATE/DELETE

auth_factors(id, user_id, task_id, factor_type, status, verified_at, attempt_count)
  -- factor_type: sms|fingerprint|face|ushield

risk_events(id, user_id, session_id, kind, severity, detail_json, created_at)
  -- kind: injection_detected|prompt_denied|velocity|amount_spike|novel_recipient

denials(id, user_id, session_id, requested_action, reason_code, audit_seq)
  -- 每次拒绝都要落表并挂审计链，安全自评报告直接引这表
```

### 3.1 三条硬规则

1. **禁止 Agent 新增收款人。** 只能从已有联系人里选；用户要转给新账号，必须走人工流程。
   这一条直接砍掉「诱导转账给陌生账户」的整类攻击。
2. **禁止 Agent 读取验证码 / 代填因子。** 因子验证必须由前端原生控件完成，Agent 只传 task_id。
3. **禁止 Agent 执行 change_password / add_contact / 任何未注册工具。**
   工具注册表是白名单，未知工具直接落 denials 表。

## 4. 状态机

### 4.1 任务状态

```
                ┌──────────┐
                │ planning │
                └────┬─────┘
                     │ DAG 生成
                     ▼
                ┌──────────┐  需确认   ┌──────────────────┐
                │ running  ├─────────►│ awaiting_confirm │
                └────┬─────┘           └────────┬─────────┘
        需强验证      │                          │ 用户确认
        ┌────────────┴──────┐                   │
        ▼                   ▼                   ▼
┌─────────────────┐   ┌───────────┐      （回到 running）
│ awaiting_factor │   │ completed │
└────────┬────────┘   └───────────┘
         │ 因子通过              ▲
         └───────────────────────┘

任意状态 → paused（用户中断）/ failed（不可恢复）/ cancelled / escalated（转人工）
paused → running（恢复，节点状态保留）
```

### 4.2 资金状态

```
      transfer_hold
           │
           ▼
     ┌──────────┐  超时/用户取消   ┌──────────┐
     │  held    ├────────────────►│ released │
     └────┬─────┘                 └──────────┘
          │ 因子通过 + commit
          ▼
     ┌───────────┐
     │ committed │  ← 不可逆，只能走补偿交易
     └───────────┘
```

**关键不变式**：available_cents = balance_cents - Σ(held.amount)，且恒 >= 0。
这条不变式要写成单测，每次 commit 前后校验。

## 5. 三色规则表（策略引擎的唯一依据）

规则是**有序的**，命中第一条即返回。

| 序 | 条件 | 判定 | 附加要求 |
|---|---|---|---|
| 1 | tool ∈ GREEN 白名单 | 🟢 自动执行 | 记审计 |
| 2 | tool ∉ 注册表 | ⛔ 拒绝 | 记 denial |
| 3 | 调用者身份来自话术而非 token | ⛔ 拒绝 | 记 denial |
| 4 | tool ∈ RED 集合（freeze/unfreeze/password） | 🔴 | 强因子 + 人工确认 |
| 5 | amount >= HARD_CAP（5万） | 🔴 | 强制转人工，Agent 不得继续 |
| 6 | amount > 0 且（日累计 + amount）> 1000 | 🔴 | 强因子 |
| 7 | 收款人是新的（use_count=0 或上次>90天）且 amount > 200 | 🔴 | 强因子 + 二次确认文案 |
| 8 | amount + 日累计 <= 1000 | 🟡 | 用户点确认 |
| 9 | 其它写操作 | 🟡 | 用户点确认 |
| 10 | 熔断激活（连续失败≥3 或 1分钟>5次写） | ⛔ 拒绝 + 锁 5 分钟 | 记 risk_event |

### 5.1 必须处理好的边界

| 边界 | 答案 |
|---|---|
| 日累计按什么重算 | 自然日 00:00 本地时区，含已提交 + 已冻结，不含已释放 |
| 跨渠道怎么算 | 合并计算（APP + IM + 语音同一个池子） |
| 23:59 转 999，00:01 再转 999 | 两次都是 🟡，因为已跨日重置 —— **这是已知风险，写进安全自评** |
| 冻结中的钱算不算可用 | 不算。available = balance - held |
| 金额边界（正好 1000） | 按题目原文「≤1000 为黄色」，1000 是 🟡，1000.01 才 🔴 |
| 理财申购金额 | 无论多少都是 🔴（题目明确） |
| 用户说「我确认过了」 | 不构成确认。确认必须是结构化事件（pending_id + 时间戳 + 因子结果） |

## 6. API 契约

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /api/session | 建会话，返回 session_id + trust_level |
| POST | /api/chat | SSE 流式对话；事件：token / trace / confirm / factor / done |
| POST | /api/confirm | 入参 pending_id + decision（accept 或 reject） |
| POST | /api/factor/verify | 入参 task_id + factor_type + proof（proof 由前端原生控件产出） |
| POST | /api/task/{id}/pause | 中断 |
| POST | /api/task/{id}/resume | 恢复 |
| GET | /api/trace/{task_id} | 完整决策链（供剧场回放） |
| GET | /api/audit/verify | 校验哈希链，返回首个断裂点 |
| POST | /api/admin/switch-profile | 切 cloud / local / adversarial（仅 dev） |
| POST | /api/admin/run-redteam | 跑攻击套件，返回每条的拦截结果 |

### 6.1 SSE 事件（前端按此渲染剧场）

event: trace  →  data: stage=intent, payload=意图与槽位
event: trace  →  data: stage=plan, dag=节点与依赖
event: trace  →  data: stage=policy, level=yellow, reasons=命中规则列表
event: confirm → data: pending_id + 结构化确认卡片
event: trace  →  data: stage=audit, seq + hash
event: done   →  data: receipt 摘要

**剧场必须是实时流式的**，不是跑完再显示。
评委看到判决灯一个个亮起来，才有「机制在工作」的感觉。
