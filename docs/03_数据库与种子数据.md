# 03 数据库与种子数据

## 3.1 全局约定

| 约定 | 规则 |
|---|---|
| 金额 | 一律 `INTEGER`，单位**分**，字段名以 `_fen` 结尾。禁止 REAL |
| 时间 | 一律 `INTEGER`，Unix 毫秒，字段名以 `_ms` 结尾 |
| 主键 | `TEXT`，格式 `前缀_8位十六进制`（用 `ids.new_id()`） |
| 枚举 | `TEXT` + `CHECK` 约束，不用整数码 |
| 外键 | 一律声明 `REFERENCES`，连接时 `PRAGMA foreign_keys=ON` |
| 布尔 | `INTEGER` 0/1 |
| 索引 | 每个外键列 + 每个高频查询条件列 |

打开连接时必须执行：

```sql
PRAGMA journal_mode=WAL;
PRAGMA foreign_keys=ON;
PRAGMA busy_timeout=5000;
```

### 6) holds —— 资金冻结（两阶段的第一阶段）

```sql
CREATE TABLE holds (
  id               TEXT PRIMARY KEY,
  account_id       TEXT NOT NULL REFERENCES accounts(id),
  payee_id         TEXT NOT NULL REFERENCES payees(id),
  amount_fen       INTEGER NOT NULL CHECK (amount_fen > 0),
  note             TEXT NOT NULL DEFAULT '',
  status           TEXT NOT NULL CHECK (status IN ('held','committed','released','expired')),
  idempotency_key  TEXT NOT NULL UNIQUE,
  session_id       TEXT NOT NULL,
  created_ms       INTEGER NOT NULL,
  expires_ms       INTEGER NOT NULL,
  settled_ms       INTEGER
);
CREATE INDEX idx_holds_sweep ON holds(status, expires_ms);
```

**为什么必须有**：转账是双写（扣钱 + 记账）。任一步失败都可能让钱凭空消失或凭空出现。hold 把这两步拆成「先占位、再落账」，中间崩溃可由清扫任务兜底。

**`idempotency_key` 唯一约束**：用户手抖点两次确认、或网络重试，第二次会撞唯一约束 → 服务端捕获后返回既有 hold，而不是扣两次钱。

### 7) audit_log —— 审计链（**只增不改**）

```sql
CREATE TABLE audit_log (
  seq          INTEGER PRIMARY KEY AUTOINCREMENT,
  ts_ms        INTEGER NOT NULL,
  session_id   TEXT,
  task_id      TEXT,
  event_type   TEXT NOT NULL,
  payload_json TEXT NOT NULL,
  prev_hash    TEXT NOT NULL,
  hash         TEXT NOT NULL
);
CREATE INDEX idx_audit_session ON audit_log(session_id, seq);

CREATE TRIGGER audit_no_update BEFORE UPDATE ON audit_log
BEGIN SELECT RAISE(ABORT, 'audit_log is append-only'); END;

CREATE TRIGGER audit_no_delete BEFORE DELETE ON audit_log
BEGIN SELECT RAISE(ABORT, 'audit_log is append-only'); END;
```

**哈希定义（必须逐字节一致，否则演示时校验会挂）**：

```
material = prev_hash + '|' + str(ts_ms) + '|' + event_type + '|' + payload_json
hash     = sha256(material.encode('utf-8')).hexdigest()
prev_hash 取上一条的 hash；表为空时用 'GENESIS'
payload_json 必须是 json.dumps(payload, ensure_ascii=False, sort_keys=True, separators=(',',':'))
```

`event_type` 取值闭集：`session.start` `intent.parsed` `dag.built` `policy.decided` `confirm.requested` `confirm.approved` `confirm.rejected` `token.issued` `token.rejected` `transfer.initiated` `transfer.committed` `transfer.released` `tool.executed` `injection.detected` `breaker.open` `session.end`。

### 8) sessions —— 会话

`id` PK、`created_ms`、`last_ms`、`title`、`status` CHECK IN ('active','done','cancelled')。

### 9) dag_runs —— 一次规划执行

`id` PK、`session_id` REFERENCES sessions、`dag_json`、`status` CHECK IN ('running','waiting','done','failed','cancelled')、`created_ms`、`updated_ms`。

### 10) dag_nodes —— 节点状态

`id` PK、`run_id` REFERENCES dag_runs、`node_id`（如 `n3`）、`tool`、`params_json`、`state` CHECK IN ('pending','running','waiting_confirm','waiting_factor','done','failed','skipped')、`decision_json`、`result_json`、`ts_ms`。

### 11) confirmations —— 待确认动作

```sql
CREATE TABLE confirmations (
  id           TEXT PRIMARY KEY,
  session_id   TEXT NOT NULL,
  run_id       TEXT NOT NULL,
  node_id      TEXT NOT NULL,
  action_json  TEXT NOT NULL,
  status       TEXT NOT NULL CHECK (status IN ('pending','approved','rejected','expired')),
  created_ms   INTEGER NOT NULL,
  expires_ms   INTEGER NOT NULL,
  resolved_ms  INTEGER
);
```

**写入时机（四个点，缺一个就会出现「卡片状态是假的」）**：

| 时机 | 代码 | status |
|---|---|---|
| 建卡（`new_confirmation`，唯一入口） | `app/planner/state.py` | `pending`，同时写 `created_ms` / `expires_ms` |
| 用户批准或拒绝（`resolve_confirmation`） | `app/planner/state.py` | `approved` / `rejected`，写 `resolved_ms` |
| 120 秒无人应答（`executor._timeout`） | `app/planner/executor.py` | `expired`，写 `resolved_ms`，同时释放预授权 |
| 红灯但无因子可验（`executor._blocked`） | `app/planner/executor.py` | `expired`（这张卡没有「就这么办」的出口） |

> 后两条**不经过** `resolve_confirmation`（它们不唤醒执行器、写的也是不同审计），所以统一走 `state.mark_confirmation` 落库。历史上这张表只有 UPDATE 没有 INSERT，于是「表在、SELECT 在、代码看着有实现，实际一行没写过」，`/api/session` 永远列出空数组。

**重启后是什么状态**：卡片行还在，`/api/session` 能按 `session_id` 把它列出来（供页面刷新恢复现场）；但内存里的 `future` 随进程消失，所以**列出的是它最后一次落定的状态，不可再作答**——一个 `pending` 行在进程重启后不会再等任何人。这是刻意的口径，不是缺陷。

### 12) token_nonces —— 防重放

`nonce TEXT PRIMARY KEY`、`used_ms INTEGER NOT NULL`、`expires_ms INTEGER NOT NULL`。签发时插入；插入冲突说明重放，直接拒。

### 13) subs —— 订阅/代扣

`id`、`account_id`、`merchant`、`amount_fen`、`period` CHECK IN ('monthly','yearly')、`next_charge_ms`、`status` CHECK IN ('active','cancelled')；2026-10-24 追加 `source`（recorded / inferred）、`confidence`（0–1）、`evidence_json`（推断依据的流水 id 与间隔）。

### 14) daily_limits —— 日累计（三色黄线的依据）

```sql
CREATE TABLE daily_limits (
  account_id  TEXT NOT NULL,
  day         TEXT NOT NULL,
  spent_fen   INTEGER NOT NULL DEFAULT 0,
  tx_count    INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (account_id, day)
);
```

`day` 格式 `YYYY-MM-DD`（本地时区）。**每次 decide 读、每次 commit 写**，同一事务内完成。

### 15) denials —— 被拒记录

`id`、`session_id`、`reason`、`action_json`、`ts_ms`。用于熔断统计和答辩展示「我们拦了多少」。

### 16) 2026-10-24 新增的 4 张表（一句话职责）

| 表 | 职责 | 关键约束 |

| `factor_challenges` | 多因子挑战：服务端下发、服务端校验的一次性验证码 | 只存 `sha256(secret|challenge_id|code)`，绝不明文；5 分钟过期；`attempts` 上限 5 次；`used_ms` 非空即已用；绑定 `(session_id, confirmation_id, factor)` |
