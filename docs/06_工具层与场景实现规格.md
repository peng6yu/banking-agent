# 06 工具层与场景实现规格

## 6.1 工具清单（**权威表，以此为准**）

| # | 工具 | 类型 | 颜色 | 说明 |
|---|---|---|---|---|
| 1 | `query_balance` | 只读 | green | 查余额 |
| 2 | `query_transactions` | 只读 | green | 查流水（可按分类/时间/金额过滤） |
| 3 | `analyze_bill` | 只读 | green | 账单统计与异常识别 |
| 4 | `list_subs` | 只读 | green | 列出订阅代扣 |
| 5 | `list_cards` | 只读 | green | 列出卡片 |
| 6 | `resolve_payee` | 只读 | green | 按姓名/别名查收款人，可能返回多条 |
| 7 | `transfer` | 写 | 按金额 | 转账（两阶段） |
| 8 | `cancel_subscription` | 写 | yellow | 取消订阅 |
| 9 | `reserve_funds` | 写 | 按金额 | 为未来需求锁定资金（hold，不立即扣） |
| 10 | `pay_merchant` | 写 | 按金额 | 向商户下单支付（如鲜花） |

> 注：`05 章 R05` 里举例的「申请虚拟卡/设置限额」属于**可选扩展**，本轮不实现。金额规则作用于 `SPEND_TOOLS = {transfer, reserve_funds, pay_merchant}`。

## 6.2 工具定义规范

每个工具在 `app/tools/registry.py` 注册，定义三件事：

```python
{
  'name': 'transfer',
  'description': '向指定收款人转账，金额单位为分',
  'params': {  # JSON Schema，直接喂给模型
    'type': 'object',
    'properties': {
      'payee_id': {'type': 'string', 'description': '收款人 ID，必须来自 resolve_payee' },
      'amount_fen': {'type': 'integer', 'minimum': 1, 'maximum': 100000000},
      'note': {'type': 'string', 'maxLength': 100}
    },
    'required': ['payee_id', 'amount_fen'],
    'additionalProperties': False
  },
  'handler': transfers.initiate,
  'writes': True
}
```

| 规范 | 要求 |
|---|---|
| `additionalProperties: False` | 防止模型塞多余参数 |
| 金额参数一律 `integer` + `minimum` | 模型不容易给小数 |
| `description` 写成一两句中国话 | 模型选工具靠它 |
| 写工具必须 `writes: True` | 执行器据此决定是否要 token |
| 每个 handler 第一个可执行语句 | `require_token(tool, params, token)` |

## 6.3 逐工具分支表

### `query_balance`

参数：`account_tail`（可选，缺省用主账户）。返回：`{accounts: [{tail, name, balance_fen}]}`。

| 条件 | 行为 |
|---|---|
| 未给 `account_tail` | 返回全部账户，主账户排第一 |
| 给了但不存在 | `ToolResult(ok=False, error_code='ACCOUNT_NOT_FOUND')` |
| 正常 | 返回余额，**附带 `balance_fen` 与 `balance_yuan` 两个人话字段** |

### `query_transactions`

参数：`days`（默认 30）、`category`（可选）、`min_fen`/`max_fen`（可选）、`limit`（默认 20，上限 100）。

| 条件 | 行为 |
|---|---|
| `days > 365` | 截断到 365 并在 `data.truncated=True` 说明 |
| 结果为空 | `ok=True` + `data.empty=True`，**不要报错**（空结果是正常业务状态） |
| 分类不在枚举 | `ok=False, error_code='BAD_CATEGORY'`，并把合法分类列给模型 |

### `analyze_bill` —— 场景 2 的核心

参数：`period` ∈ {`month`,`year`}、`year`、`month`。返回结构**必须固定**：

```python
{
  'total_out_fen': 0, 'total_in_fen': 0,
  'by_category': [{'category': '餐饮', 'amount_fen': 0, 'count': 0, 'pct': 0.0}],
  'top_merchants': [{'merchant': '...', 'amount_fen': 0, 'count': 0}],
  'anomalies': [
    {'kind': 'split_orders', 'title': '短时拆单', 'detail': '...', 'amount_fen': 0},
    {'kind': 'odd_hour_overseas', 'title': '境外深夜消费', 'detail': '...'},
    {'kind': 'subscription_hike', 'title': '订阅涨价', 'detail': '...'}
  ]
}
```

| 条件 | 行为 |
|---|---|
| 该期间无流水 | `ok=True`，`total_out_fen=0`，`anomalies=[]`，并给一句人话 |
| 分类金额并列 | 按金额降序，金额相同按分类名字典序（**保证可复现**） |
| 异常检测 | 三条规则见下 |

异常检测规则（固定实现，不要自由发挥）：

| kind | 判定 |
|---|---|
| `split_orders` | 同一 `counterparty` 在 60 分钟内出现 ≥3 笔且单笔在 500—1000 元之间 |
| `odd_hour_overseas` | 本地时间 00:00—05:00 且 `counterparty` 含境外标识（种子数据里标记为境外商户）且单笔 ≥ 500 元 |
| `subscription_hike` | 同一商户连续两个月扣款，后一月比前一月高 ≥ 30% |

### `resolve_payee`

参数：`name`（姓名或别名）。

| 条件 | 行为 |
|---|---|
| 0 条 | `ok=True, data.candidates=[]` → 上层走「没找到」分支 |
| 1 条 | 返回唯一候选 |
| ≥2 条 | `ok=True`，返回候选列表，**必须带 `card_tail` 供用户区分** |

### `transfer`（两阶段，见 05 章 5.4）

参数：`payee_id`、`amount_fen`、`note`。返回：`hold_id`、`status`。

| 条件 | 行为 |
|---|---|
| 无 token | 抛 `MissingCapability` |
| `payee_id` 不存在 | `ok=False, error_code='PAYEE_NOT_FOUND'` |
| 余额不足 | `ok=False, error_code='INSUFFICIENT_FUNDS'` + 差额 |
| 正常 | 建 hold，返回 `hold_id`，**此时还没扣钱** |

### `cancel_subscription`

参数：`sub_id`。

| 条件 | 行为 |
|---|---|
| 已是 `cancelled` | 幂等返回成功 |
| 不存在 | `SUB_NOT_FOUND` |
| 正常 | 改状态，写审计，返回下次扣费已取消 |

### `reserve_funds`

参数：`amount_fen`、`purpose`（如 生日)。行为同 transfer 的 hold，但**不产生转账流水**，只是锁定。

| 条件 | 行为 |
|---|---|
| 余额不足 | `INSUFFICIENT_FUNDS` |
| 正常 | 建 hold（`payee_id` 填系统占位 `p_system`），返回 `hold_id` 与 `expires_ms` |

### `pay_merchant`

参数：`merchant`、`item`、`amount_fen`、`hold_id`（可选，用于复用已有预留）。

| 条件 | 行为 |
|---|---|
| 给了 `hold_id` 且有效 | 用该 hold 的额度，直接 commit |
| `hold_id` 过期 | 返回 `HOLD_EXPIRED`，上层走「重新确认」分支 |
| 商户不在白名单 | `MERCHANT_NOT_ALLOWED`（白名单：`flower_shop`、`cake_shop`） |
| 正常 | 建 hold 并立即 commit |

## 6.4 场景 1：智能转账（做深）

### 主链路

| 步 | 输入/事件 | 期望行为 | 分支 |
|---|---|---|---|
| 1 | 用户：转 500 给李静，备注生日祝福 | 解析出 payee=李静 amount=500 note=生日祝福 | 见分支表 |
| 2 | 解析结果 | `resolve_payee('李静')` | 0 条→没找到；≥2 条→列候选 |
| 3 | 唯一候选 | 生成 DAG：`n1 resolve_payee → n2 query_balance → n3 transfer` | — |
| 4 | 执行 n1 n2 | green，直接跑 | — |
| 5 | n3 裁决 | 500 元 ≤ 1000 → yellow | — |
| 6 | 暂停 | SSE 发 `confirm`，含人话解释 | 120 秒无响应→`confirm.expired` |
| 7 | 用户点确认 | 签发 token（绑定 payee/amount/note） | — |
| 8 | 执行 transfer | 建 hold → commit → 扣款 → 写流水 | 余额不足→提示差额 |
| 9 | 收尾 | SSE `done`，剧场显示扣款前后余额 | — |

### 分支表（**每个都必须实现，红队会打**）

| # | 分支 | 触发 | 行为 | 话术 |
|---|---|---|---|---|
| B1 | 缺收款人 | slots 无 payee | 不规划 DAG，直接反问 | 请问转给谁？ |
| B2 | 缺金额 | slots 无 amount | 反问 | 转多少？ |
| B3 | 收款人 0 条 | candidates 空 | 反问 + 提示可先添加 | 通讯录里没有叫 X 的人，要新增吗？ |
| B4 | 收款人多条 | candidates ≥2 | 列候选并让用户选 | 有两位叫张三，是尾号 1234 还是 5678？ |
| B5 | 金额口语化 | 五百五 / 全部 | 走 `parse_amount` | 「全部」需先查余额再复述确认 |
| B6 | 超黄线 | amount > 1000 元 | 走 red，要求双因子 | 超过 1000 元需要人脸和短信验证 |
| B7 | 日累计超线 | spent+amount > 1000 元 | 同上 | 今日已转 X 元，再转将超过 1000 元 |
| B8 | 余额不足 | balance < amount | 不建 hold | 卡里只有 X 元，还差 Y 元 |
| B9 | 备注含注入 | note 命中 injection | 标 `untrusted_fields=['note']` → R04 → red | 这条备注看起来像指令，已升级为人工核实 |
| B10 | 确认超时 | 120 秒未响应 | 作废 confirmation，写审计 | 这笔转账已超时取消 |
| B11 | 重复确认 | 同一 confirmation 二次提交 | 幂等，返回第一次的结果 | — |
| B12 | commit 时 hold 过期 | 超过 300 秒 | `HoldExpired`，提示重新发起 | 操作超时，请重新发起 |

## 6.5 场景 2：账单分析（中等深度）

## 6.6 场景 6：跨场景联动（做深，答辩主秀）

用户：下周三是我妈生日，帮我准备一下。

### DAG（4 步，必须有环检测与中断）

```
n1 resolve_payee(老妈)         green
n2 query_balance               green
n3 reserve_funds(300元, 生日)  yellow → 确认
n4 pay_merchant(flower_shop)   yellow → 确认（复用 n3 的 hold）
```

### 分支表

| # | 分支 | 行为 |
|---|---|---|
| B1 | 找不到收款人「老妈」 | 用别名匹配（`payees.alias`），仍无则跳过记账只做提醒 |
| B2 | 余额不足以覆盖 300 元 | 降级：只生成提醒，不锁资金（`skipped` 节点要显示原因） |
| B3 | 用户在第 3 步拒绝 | 回退：n3 已建 hold 则 `release`，n4 标 `skipped` |
| B4 | 用户在第 4 步拒绝 | n3 的 hold 保留（钱还在自己账上），提示「预算已保留，你随时可以再下单」 |
| B5 | 中途说「算了」 | `cancel`：释放全部 hold，DAG 全标 `cancelled`，写审计 |
| B6 | 商户白名单外 | `MERCHANT_NOT_ALLOWED`，不执行，提示可选商户 |

**这个场景的评分意义**：同时展示多步规划、资金预留、人工确认、回退、降级五个能力，是 30% 创新分的主要来源。

## 6.7 场景 5：订阅一键取消（t47 新增）

用户：帮我把爱奇艺会员那个自动续费关掉。

### DAG（2 步，先列后取消）

```
n1 list_subs                         green
n2 cancel_subscription(sub_id)       yellow → 确认（R05_confirm_only）
```

### 分支表

| # | 分支 | 行为 |
|---|---|---|
| B1 | 只说「把订阅都关了」，没点名是哪一条 | 反问「要取消哪一条订阅？请说订阅名称……」，**绝不批量取消** |
| B2 | 名字对不上（用户说「视频会员」，名下没有） | 反问并列出名下订阅，**cancel_subscription 不会被调用** |
| B3 | 名字对得上多条 | 反问并列出候选，请用户点名，**绝不替用户挑一条** |
| B4 | 用户在确认卡上点「不」 | 订阅状态不变，写 `confirm.rejected`（reason=`USER_REJECTED`），本步终止 |
| B5 | 用户点头 | 写工具带 `require_token` 执行，`subs.status` 由 `active` 改成 `cancelled`，审计记 `tool.executed`（`state_change=active->cancelled`） |
| B6 | 只是查订阅（原话里没有取消动作词） | 只走 `n1 list_subs`，**DAG 里根本没有取消节点** |

**这条场景的意义**：它是「写操作的三道闸」——意图层按用户原话分流（查 / 取消）、
规划层按名字唯一匹配（匹配不上就问）、策略层黄灯确认（`R05_confirm_only`）。
退订错一条比多问一句糟得多，所以任何一道闸没过，订阅状态都不动。

## 6.8 工具层禁止事项

| 禁止 | 原因 |
|---|---|
| 在工具里判断「该不该做」 | 那是 policy 的活，工具只执行 |
| 直接 `UPDATE accounts SET balance_fen=...` 绕过 hold | 破坏两阶段 |
| 用 `requests` / `urllib` 调外部服务 | 本轮全部 mock，禁止真实支付 |
| 在工具里调用 LLM | 执行层不许有模型 |
| 静默吞掉异常返回 `ok=True` | 会让审计失真 |
