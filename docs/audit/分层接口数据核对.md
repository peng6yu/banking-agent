# 分层接口数据核对：每一层都清楚自己那份数据吗

> 版本 v1.0 · 2026-10-26 · 只读核对（三路并行审计 + Lead 复核），行号为当前工作树。
> 核对对象：页面（web/）→ HTTP 接口（51 条路径 / 57 个方法）→ 视图与用例（app/views、app/use_cases）→ 领域（app/*.py）→ 数据库（36 张表）。

## 0. 先给结论

1. **「谁调谁」是清楚的**：依赖方向由 tests/test_imports.py 的 LAYERS 钉住，跨层违规 0 条；每一层都只往下要数据。
2. **「同一份数据长什么样」不清楚**：读端点没有统一信封，同一概念最多 5 种形状（余额），结余 3 种口径，确认卡 3 面，审计 3 形状。
3. **每一层都能拿到「自己那一份」**，但**没有一层对「统一形状」负责**：视图各自 SELECT、各自拼 dict；路由有 4 处绕过视图；前端只能靠字段探测 + 兜底。
4. **页面只用了 51 条路径中的 40 条**（剩下 1 条是根路径 /，由浏览器直接打开），10 条接口页面到不了；其中 handoffs 的列表/详情/创建三个端点**页面一个入口都没有**，GET /api/investment/suitability 是唯一带评分暴露性质的孤儿。
5. **计数全部是「本页条数」**，全库没有 total；安全页「待接管 N」会随分页/上限跳动——这是最容易被当成「数据错了」的一类。
6. **金额的存储口径是统一的（整数分）**，元的字符串只有 app/money.py:68-73 一份实现，但前端仍出现 /100（web/js/88-view-monitor.js:75），说明「元/分」没有在契约层被约束。
7. **时间文本有 2 种精度、4 套实现**：同屏会出现「07-03 14:20」与「2026-07-03 14:20」；/api/session、goals、alerts 甚至只有毫秒没有文本。

## 1. 五层盘点（每层拿什么、缺什么）

| 层 | 规模 | 谁定义数据形状 | 现状 | 清楚度 |
|---|---|---|---|---|
| L5 页面 | 6 页签、18 个 js | 直接读 JSON 字段，字段缺失靠 textOf/BX_NA 兜底 | 40 条路径被调用；A/B/C 三类契约缺口共 18 处 | 基本清楚（有兜底，但缺字段无人报警） |
| L5 API/视图 | 8 个 router、57 个方法、10 个 view 模块 | 写端点统一 payload()；读端点各自拼 | 两套信封；4 处路由绕过视图 | 不清楚（没有契约层） |
| L4 用例 | 14 个模块 | Outcome → payload，一个写操作一个事务 | 形状统一，是最好的一层 | 清楚 |
| L3 领域 | funds/plans/proactive/subscriptions/birthday 等 | 各自返回 dict，金额分、时间 ms | 同概念在不同领域模块里形状不同 | 基本清楚 |
| L2 策略/仓储 | policy 13 条规则、handoff_store | Decision / 快照 | 纯函数，字段稳定 | 清楚 |
| L1 基础/DB | 36 张表、audit/token/factors | db.py 只约定「分/毫秒/TEXT 主键」 | 读口径没有单一实现（20+ 处直写 SQL） | 存储清楚，读口径不清楚 |

## 2. 页面 → 接口：谁在用哪条

六个页签的主体数据只靠 5 个只读快照端点：/api/business/{overview,bill,plans,management,executions}；写操作全部走独立端点。

| 页签 | 端点 | 说明 |
|---|---|---|
| 总览 | business/overview + messages | 余额、本月收支、异常、待授权、储蓄目标、计划提醒、接管单、助手提醒 |
| 助手 | chat（SSE）、confirm、cancel、factor/challenge、audit、tools、session | 执行主链路 |
| 账单 | business/bill、transactions/manual、scheduled/run | 汇总 + 补录 + 到期执行 |
| 计划 | business/plans、plans/*、savings/goals、proactive/* | 计划与提醒的读写都在这里 |
| 业务管理 | business/management、subscriptions/verdict、memory、investment/suitability(POST) | 卡、订阅、理财、记忆 |
| 执行记录与安全 | business/executions、handoffs 动作、scheduled challenge/verify、audit | 追溯与强验证 |

前端逐页核对出的三类缺口（完整表见 tmp/layer_1_frontend_api.md）：

**A 前端读了、后端没给（5 处）**

**B 后端给了、前端没读（8 处，节选）**：计划页整块 pending_authorizations（app/views/plans.py:68 vs web/js/84-view-plans.js 全文）；首页 top_merchants（app/views/overview.py:72）；账单 method 口径说明（app/views/bill.py:83-89）；done.conflict / error.trace_id（app/planner/executor.py:149、app/api/chat_flow.py:345-347）。

## 3. API 层：57 个方法、两套信封

- **写端点**统一：用例返回 Outcome → app/api/http.py:10-18 payload() → {ok: true, ...}；异常统一由 app/main.py:121-149 翻成 {code, user_text}。这层是干净的。
- **读端点**各自为政：business 5 个裸 view；messages/handoffs 裸 dict；session/audit/memory/savings/suitability/alerts/plans 手写 {ok: true, ...}；confirm/cancel/recover 直接返回执行器结果。
- **4 处路由绕过视图**：GET /api/session/{id}（app/api/chat_api.py:176-212，自写 SQL + _card_view 重建确认卡）、GET /api/audit（app/api/core_api.py:50-74）、GET /api/memory（app/api/memory_api.py:50-61）、GET /api/handoffs（app/api/handoffs_api.py:54-62）。
- **视图直写 SQL 20+ 处**：app/views/queue.py:98-104 已是 confirmations×dag_runs×dag_nodes 的三表 LEFT JOIN，不等于「装配」；views/money.py:53-56、166-170；views/executions.py:35-37；views/management.py:48-51 等。
- 后果：读侧没有单一查询层，同一条数据被 3-4 个文件各自 SELECT，字段别名随之漂移（balance_fen、amount_fen、id/transaction_id、counterparty/merchant）。

## 4. 领域/DB 层：单位一致、格式化与形状不一致

| 主题 | 权威实现 | 偏离 |
|---|---|---|
| 分→元 | app/money.py:68-73（千分位+两位） | web/js/88-view-monitor.js:75 直接 /100 |

## 6. 风险与修法（不改码，只给方向）

| 级别 | 问题 | 建议 |
|---|---|---|
| P0 | count=本页条数、无 total（安全页「待接管 N」不可信） | 列表统一 {items,count,total,limit}；count=本页、total=满足条件总数 |
| P0 | GET suitability 泄露评分与分级 | 服务端只下发脱敏问题（与 management 同源），或直接下线该 GET |
| P1 | 4 处路由自拼 + 确认卡 3 面 | 抽 views/confirmations.py，SSE 与刷新共用同一函数 |
| P1 | 审计 3 形状 + 前端两套解析（web/js/50-actions.js:199-201 拉 /api/audit 永远空，因为后端只给 events） | 统一 {events,count,chain_ok,chain_head,append_only} |
| P1 | A1/A3/A4/A5 前端读不到（有兜底但显示英文/空） | 后端补 period_label、reason_label（或前端用中文映射）、session 补 state_label、confirm 加 expired 分支 |
| P2 | 结余 3 口径无标签 | bill 返回 nets:[{key,label,fen,yuan}]，前端不再猜 |
| P2 | 读端点两套信封 | 统一 {ok:true,...} 或统一裸 view + 全局错误体 |
| P2 | 时间 4 套实现 | 全部走 app/timefmt.py；列表统一 minute_text，卡片统一 stamp_text |

## 7. 逐层「清楚了吗」的回答

- **用例层（L4）清楚**：一个写操作 = 一个事务 + 一个 Outcome，异常只翻译一次。
- **策略层（L2）清楚**：Decision 字段稳定，13 条规则顺序即优先级。
- **视图层（L5）基本清楚但不统一**：每个 view 都能自洽地拼出一页，但同概念在不同 view 里有不同形状，没有人负责「统一」。
- **接口层（L5）不清楚**：57 个方法里 2 套信封、4 处绕过视图、10 个页面到不了。
- **前端（L5）是「能显示」而不是「契约驱动」**：靠 textOf/BX_NA 兜底，缺字段不会报错也不会告警，A1/A3/A4/A5 就是这样活下来的。
- **数据库（L1）存储清楚、读口径不清楚**：36 张表的单位与主键有约定，但读侧 20+ 处直写 SQL。

**一句话**：这不是「某一层漏了数据」，而是**缺少一层「接口契约」**——把「同一概念只有一个形状、每个读端点都带 total 与文本时间、页面用到的字段都有中文兜底」变成可测试的约定。补上这一层，六页签的数据才算真正「每层都清楚」。
