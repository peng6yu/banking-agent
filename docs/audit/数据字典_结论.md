## 附录A. 一句话结论

底层数据是干净的：金额一律存分、时间一律存毫秒、结构化内容一律存 JSON 文本、主键一律带前缀、命名违规自动检查 0 条。
**乱在「出口」——同一个概念在不同接口有 2-5 种形状，前端只能各自兜底。**所以「把所有数据搞清楚」的落点不是再盘点一遍字段，而是给每个概念定一个形状、一个落点，然后让所有出口都吐它。

> **2026-10-26 深夜第二次收口**：单位配对缺口已从 36 组压到 **0 组**（`_fen` 必配 `_yuan`、`_ms` 必配 `_text`），11 个读端点统一带 `ok:true`，`message_feedback` 表与 subs 三个死列已删，`monitor_rules.threshold` 已拆成 `threshold_fen`/`threshold_pp`，`cards.pin_hash` 已接上旧密码校验，`GET /api/messages/insights` 已删。剩余见附录 D/E/F 的「已修/未修」标注。

## 附录C. 单位与量纲（对外契约）

- 金额：DB 存**分**（`*_fen`，INTEGER），接口**成对**给 `*_fen` 与 `*_yuan`（字符串，千分位两位小数），页面**只渲染 `*_yuan`**，禁止再 `/100`。现存违例：`web/js/88-view-monitor.js:75`。
- 时间：DB 存**毫秒**（`*_ms`，UTC 毫秒，按服务器本地时区解释），接口成对给 `*_ms` 与 `*_text`。
- 百分比：`*_pct` 为整数百分比（52 表示 52%），不存 0.52。
- 比例/占比：页面本地算，不落库、不进接口。
- 条数：只给「本页条数」，字段名必须自证（见上表计数行）。

## 附录F. 仍然不清楚的部分（诚实清单）

1. **枚举双处维护**：状态值域既在 DB `CHECK` 约束里，也在代码常量里（如 `app/views/labels.py`），字典只能看到「库里出现过的值」。→ 建议把常量作为唯一来源生成 CHECK，或加测试断言两者一致。
2. **时区**：毫秒列无时区列，一律按服务器本地时区解释；跨时区部署会错。→ 目前单机可接受，部署前必须定。
3. **写端点**：30 个写方法中只有 3 个安全端点被真实采样，其余字段形状来自 OpenAPI schema，不是实测响应。→ 需要一组「在临时库上跑一遍全写路径」的脚本，属下一轮。
4. **两个端点 0 样本**：`GET /api/handoffs/{handoff_id}`、`GET /api/plans/{plan_id}` 因库里 0 行拿不到真实响应。→ 先用 fixture 造一行再采样。
5. **前端 17 个 js 零单测**：契约缺口是人工核出来的，不是测试卡出来的。→ 本轮已补两条后端契约测试（tests/test_business_api.py 末尾：读端点必带 `ok`、`_fen` 必配 `_yuan` 且 `_ms` 必配 `_text`，递归扫 12 个端点）；前端自身仍无单测，字段消费只能靠浏览器复核。
6. **`count` 语义**：改名会破坏现有前端，属破坏性变更，需与前端一起改；本轮只登记不改。
