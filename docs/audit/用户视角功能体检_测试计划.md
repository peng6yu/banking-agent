## 0. 一句话与方法论

不是再写一遍单元测试，而是**扮演一个没看过代码的真实用户**：从"我看得见什么、我点了会发生什么、什么情况下我会以为它坏了"出发，把六个栏目的每个可见功能走一遍，并专门打**边界**（空、满、超长、超时、过期、重复、并发、断网、同名、跨栏不一致）。

已有的 1719 条 pytest + 43 条红队 + 13 步 e2e + 7 条浏览器旅程是"实现者视角"的护栏；本次体检补的是**用户可感知行为**与**护栏之间的缝**：

- 护栏证明"逻辑对"，体检问"用户会不会误解、会不会卡住、会不会看到不该看的"。
- 护栏按函数组织，体检按**用户旅程**组织。
- 护栏用 mock 模型跑得快，体检要包含**真模型下的口语化变体**（限量）。

## 3. 五层方法（L0–L4）

| 层 | 做什么 | 工具/手段 | 通过标准 |
|---|---|---|---|
| **L0 静态契约** | 前端元素与 API 字段对得上；文案与限制一致；无死链、无写死的假数据 | 读 index.html / web/js/*.js / app/views/*.py；`check_frontend.py`；grep 数字与单位 | 每个可见数字都有后端来源；每个 maxlength 与后端校验一致或更严 |
| **L1 API 契约与边界** | 47 条路径逐条打正常 + 非法 + 越界 + 未授权 | `curl`/httpx 脚本；`API_TOKEN`；`SCHEDULED_TICK_MS=0` | 错误只返回 `{code,user_text}`，无堆栈/英文异常；边界拒绝有中文解释 |
| **L2 真浏览器脚本** | 六栏目逐元素点击、表单、折叠、键盘、移动端 | `scripts/ui_journeys.py` 扩展；Playwright | 无 console error；无"点了没反应"；状态与后端一致 |
| **L3 用户探索式** | 不按脚本，按"我会怎么用"乱点：连点、返回、刷新、换标签、关页面 | 人工（我）+ 录屏；每发现一条立刻转成可复现步骤 | 每条新发现都能被 L2 复现，或明确标注"仅人工" |
| **L4 弹性与恢复** | 断网、模型 5xx、SSE 中断、服务重启、两标签并发 | 代理拦截/杀进程/拔网；`MOCK_MODE` 切换 | 有中文降级提示；刷新后不丢已完成的结果；不出现半执行状态 |

**执行比例**：L1 40%（最快找硬边界）、L2 30%、L3 20%、L4 10%。L0 在每栏开始前 10 分钟做完。

## 4. 边界条件 12 类模板

> 每类给"打哪里 + 怎么打 + 判定什么"。附录 B 会落成可勾选用例。

### B1 输入与格式
- 空提交、纯空格、500 字整、501 字（绕前端直接打 API）、emoji、全角数字"１００"、中文金额"一百块"、`+100`/`-100`/`0`/`0.001`/`1e9`、金额两位以上小数、超长商户名（39/40/41 字）、分类 12/13 字、备注 80/81 字、电话/卡号里夹 HTML 与 `'`。
- 判定：拒绝时给中文原因且指明字段；接受时数值精确到分；不产生半条记录。

### B2 状态机与幂等
- 双击"确认"、确认卡过期（>120s）后再点、澄清 chips 过期（>300s）、同一笔手动补录连点两次、同一 challenge 重放、同一因子连续错 6 次（应锁定）、九态越级（已成功之后再取消）、`/api/confirm` 重复提交同一 token。
- 判定：第二次操作有明确结果（"已处理过"或幂等成功），不能出现两条流水/两张卡。

### B3 时间与时区
- 跨零点提交、月末 31 号设 monthly（看 2 月钳制）、闰年 2/29、"明天 09:00"默认值、过去时间、`datetime-local` 无时区、浏览器时区≠服务器时区、节拍器关闭（`SCHEDULED_TICK_MS=0`）时到点计划是否仍可手动触发。
- 判定：所有"什么时候执行"在 UI 上有明确本地时间；跨时区不漂移；过期有重设入口。

### B4 金额与余额
- 可支配 ≠ 余额（生日计划预算占用）、转账后余额、超额 1 分、余额刚好等于转账额、0 元、负数冲正、999.99 / 1000.00 / 1000.01（分级阈值三点）、分/元混用、四舍五入到分。
- 判定：任一页面同一金额显示一致；拒绝时说明"可用多少、需要多少"。

### B5 权限与边界
- 无令牌访问 `/api/*`（401）、令牌错误、令牌文件缺失、`#token=` 丢失后页面壳在但数据空、只读工具试图写、跨用户 scope、同名"张三"消歧、理财"不可买"、疑似订阅"不可停"、危险动作被拒绝的话术。
- 判定：拒绝可解释、可操作；不泄露内部路径/堆栈；不出现"假成功"。

### B6 并发与竞态
- 两标签页同时点确认、同一计划连点"运行"两次、两次 ticker 同时到点、两个操作员抢同一张接管单、并发改同一储蓄目标、SSE 双连接、聊天里上一轮未结束又发一条。
- 判定：只有一个成功；另一个得到"已被处理"；金额只扣一次。

### B7 网络与降级
- 断网、SSE 建连失败/中途断、模型 5xx、模型超时（>30s）、模型返回非 JSON、模型不可用时页面其他栏目是否仍可用、刷新页面、服务重启后恢复 `/api/session/{id}/recover`。
- 判定：中文降级提示 + 重试入口；不白屏；不显示英文异常；已完成的结果不丢。

### B8 数据与空态
- 空库、无流水月份、无卡、无目标、无提醒、无接管、无审计、异常 0 条、单条流水、1000+ 条流水的分页、同名商户、乱码商户、超长备注、负数余额。
- 判定：空态有引导语（不是"加载中"卡死）；列表有上限与"更多"；分页不重复不丢。

### B9 会话与刷新
- 刷新丢当前对话、多标签同一会话、令牌仅存 sessionStorage、地址栏 token 抹除、无"退出登录"、关页面再开、跨栏目来回切换是否重复请求/重复提交。
- 判定：刷新后能看到上一轮结果与九态；不重复发请求；地址栏无敏感串。

### B10 适配与可访问性
- 375/390 手机、1440 桌面、200% 缩放、超长中文标题溢出、Tab 顺序、Enter 提交、focus 可见、折叠面板键盘可达、对比度、无鼠标完成一次转账、截图与文字说明一致。
- 判定：手机端无横向滚动条、按钮不被遮挡、表单能填完。

### B11 文案与信任
- "待核实 ≠ 欺诈"、占比含转账/理财内部搬运的说明、疑似订阅为什么不能停、理财收益/费率为什么是"—"、模型不可用文案、拒绝话术、错误码不泄露、"暂无"与"0"的区别。
- 判定：用户不会把"异常"读成"被盗"、不会把"演示数据"读成"真实收益"、不会把"不可用"读成"我操作错了"。

### B12 跨栏一致性
- 总览余额/收支 = 账单汇总；总览异常条数 = 账单异常条数；安全页九态 = 助手右栏状态；计划状态 = 计划页 = 总览；同一笔交易在三处金额/时间/商户一致；时间格式统一。
- 判定：逐项对数字，允许显示精度不同但不允许语义不同（例如一处"待确认"一处"已成功"）。

## 7. 消息互联互通（"主动大脑"）设计与验收

### 7.1 用户要的到底是什么

不是"多一个通知栏"，而是三件事：

1. **一处发生，处处知道**：转账成功、计划失败、需要接管、异常待核实、订阅涨价——不管用户当时在哪个栏目，都能看到同一条消息的同一个状态。
2. **agent 想到主人没想到的**：从已有数据里推出用户没问、但会感谢你告诉他的事（例："你连续 3 个月在 25 号前后现金紧张，要不要把房租提醒提前 3 天？"）。
3. **建议可执行、可拒绝、不越权**：点一下能进到对应操作（预填聊天或跳转确认），拒绝后不骚扰，绝不替用户动钱。

### 7.2 分层：事实层算，语言层说

```
数据（流水/计划/订阅/目标/接管/审计）
        │
        ▼
[事实层] 规则 + 统计 + 阈值  ──►  Insight{ id, kind, severity, facts, evidence, confidence }
        │                              （纯确定性、可复算、无模型）
        ▼
[时机层] 触发 + 冷却 + 频控 + 免打扰  ──►  是否现在投递、投到哪
        │
        ▼
[语言层] LLM 只做措辞与解释（输入 facts，输出受 schema 约束）
        │   数字白名单校验：输出中的数字必须出现在 facts 里，否则回落模板
        ▼
[投递层] 总览"今日建议" / 栏目内联卡片 / 站内消息中心（同一 message_id）
        │
        ▼
[反馈层] 采纳（转计划/提醒/进聊天）/ 忽略 / 不再提醒  ──►  权重与冷却
```

**硬规矩**：语言层**不得新增数字、不得新增事实、不得承诺收益、不得生成转账/支付动作**。所有"建议执行"都只是把参数填进聊天输入框，走原有确认卡与因子流程。

### 7.3 洞察目录（v1 建议 10 类，全部可从现有数据算出）

| # | 洞察 | 触发数据 | 为什么用户自己想不到 | 建议动作 |
|---|---|---|---|---|
| I1 | 订阅涨价/新增扣款 | subscriptions + 流水同比 | 小额自动扣款不引人注意 | 列出对比 + "要不要停" |
| I2 | 疑似重复扣款 | 同商户同金额 7 天内 ≥2 | 用户不会去比对 | 标"待核实" |
| I3 | 拆单/凌晨境外 | ANOMALY_KINDS | 规则细节用户不知道 | 解释规则 + 一键核实 |
| I4 | 发薪日到账 → 建议先存后花 | 流水大额入账 + 储蓄目标缺口 | 靠自觉很难 | 一键建储蓄目标/转入计划 |
| I5 | 现金缺口预警（房租/信用卡前 5 天） | 即将扣款 + 预计余额 | 心算不可靠 | 建议推迟某笔或提前备款 |
| I6 | 目标进度落后 + 三条补救路径 | 监测规则 progress | 只看到"落后"不知道怎么办 | 提高月存/延长期限/降目标 |
| I7 | 预算超支节奏（月中已用 80%） | 预算规则 budget | 月底才发现 | 给出剩余天数×日均 |
| I8 | 闲置余额 vs 可用理财（带适当性） | 余额 + 产品 + 问卷 | 不知道有更优解 | 先做问卷，不匹配就只解释 |
| I9 | 同名收款人风险 | 两个"张三" | 转错人几率高 | 提示用尾号确认 |
| I10 | 计划/接管失败未处理 | 九态里的失败/待接管 | 不常回看安全页 | 一键进接管 |

> 数量控制：每日最多 **3 条**主动消息；同一洞察同一账户 **7 天**内不重复；用户忽略 2 次后降频，忽略 3 次后进入"不再提醒"候选。

### 7.4 数据模型草案（只设计，不实现）

- `messages`：id、kind、severity、title、body、facts_json、evidence_json、confidence、created_ms、source（rule/llm）、status（unread/read/done/dismissed/snoozed）、snooze_until_ms、dedupe_key、account_id。
- `message_feedback`：message_id、action（adopt/dismiss/snooze/never）、reason、created_ms。
- 复用现有：proactive_alerts（挂 message_id）、chat runs（深链 run_id）、handoffs（深链 handoff_id）。
- 端点草案：`GET /api/messages?status=&limit=`、`POST /api/messages/{id}/read`、`POST /api/messages/{id}/dismiss`、`POST /api/messages/{id}/adopt`（返回预填的聊天参数）、`GET /api/messages/count`。

### 7.5 验收标准（消息互通）

| 维度 | 标准 |
|---|---|
| 一致性 | 同一 message_id 在总览/栏目/消息中心三处状态同步；刷新后不回退 |
| 可解释 | 100% 消息带 evidence（规则名/时间窗/涉及流水 id）；用户能点开看"为什么" |
| 不幻觉 | 语言层输出数字与 facts 不一致时自动回落模板（抽样 30 条 0 违规） |
| 不重复 | 冷却与 dedupe_key 生效（同洞察 7 天内 ≤1 条） |
| 可拒绝 | 忽略/稍后/不再提醒三档；忽略后 7 天内不再出现 |
| 可执行 | 采纳能一键进聊天或跳转对应操作，且**不绕过**确认卡 |
| 降级 | 模型不可用时规则层消息仍生成（模板文案） |
| 延迟 | 规则生成 < 2s；页面加载消息数 < 1 请求 |
| 安全 | 不新增写工具、不自动动钱；审计留痕 |
