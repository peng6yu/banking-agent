### 3.1 A1 强验证锁定可绕过（P0，详述）

**复现**（`tmp/audit/probe_factor.py`，实测）：

1. `POST /api/confirm` 造一张红灯确认 → 拿到 `confirmation_id`。
2. `POST /api/factor/challenge {confirmation_id, factor:"face"}` → 挑战 C1，`attempts_left: 5`。
3. 用错码提交 5 次 → 第 6 次即使码正确也返回 `{"status":"waiting_factor","invalid":[{"factor":"face","reason":"TOO_MANY_ATTEMPTS"}]}`（锁定生效）。
4. **再调一次 `/api/factor/challenge`** → 领到新挑战 C2，`attempts_left` 回到 5。
5. 用 C2 的正确码提交 → `{"status":"waiting_factor","missing":["sms"]}` —— 通过了。

**根因**：`attempts` 记在"挑战"这一行上（`app/security/factors.py:221-230` 只在 `CODE_MISMATCH` 时自增）；`issue()`（`:83-125`）既不查"这张确认已经签发过几次"，也没有冷却窗口。码是 6 位（`:78-80` `secrets.randbelow(10**6)`），无限制签发 = 无限制试错。

**建议修法**（最小改动）：

- `factor_challenges` 增 `issued_count` 或按 `confirmation_id + factor` 聚合；`issue()` 前查"该确认该因子已签发 ≥N 次" → 直接 `TOO_MANY_ATTEMPTS`。
- `factors.issue` 加冷却：同一 `confirmation_id` 两次签发间隔 < 3s 拒绝（`429` 语义）。
- 把锁定判据从"挑战行"上移到"确认 + 因子"级：`verify` 里累计 `failures`（任何 reason 都算），≥5 锁死到卡片过期。
- 顺带修 H26：`FACTOR_MISMATCH`（码格式/因子不符）也应计数，否则换因子名就能白刷。

**回归点**：`tests/test_factors.py` 需补三条（重复签发上限、冷却、跨挑战累计失败）。

### 3.2 A4 同屏两套口径（P1，详述）

| 位置 | 文案 | 数值 |
|---|---|---|
| 总览 KPI | 本月支出（38 笔） | 14,111.00 元 |
| 总览「近期收支」 | 结余·10 月（不含转账/理财） | 3,476.00 元 |
| 账单页统计区间 | 支出合计 / 收入合计 / 净结余 | 14,111.00 / 12,800.00 / **-1,311.00**（红） |
| 账单页月度趋势 | 10 月 支出 / 结余 | 9,324.00 / 3,476.00 |

差额 `14,111 − 9,324 = 4,787 = 理财 3,687 + 转账 1,100`。即：**支出合计含转账理财，趋势结余不含**。后端在 `app/views/money.py` 的注释里写明了"转账/理财不计入收支统计与趋势"，但账单页三个大字块用的是 `analyze_bill` 的合计，趋势用的是排除后的口径，前端把两组数并排放在一屏。

**建议**：账单页三块 KPI 改成与趋势同口径（排除转账理财），另给一行小字"含转账理财 X 元"；或统一用"全部支出"并让趋势也含。二者选一，不要并存。**同一屏出现两个"结余"是这条的地雷**。

### 3.3 A5 负结余恒正（P1，代码确证）

```python
# app/views/money.py:201-202
"net_yuan": fen_to_yuan_str(abs(net)),
"net_positive": net >= 0,
```

前端 `web/js/80-view-overview.js:43` 与 `:320` 只渲染 `net_yuan`，`net_positive` 在 `web/` 下**零引用**（grep 确认）。后果：`net = -1311.00` 的月份，趋势表"结余"列显示 `1,311.00`，与同页红色 `-1,311.00` 并存。种子数据 5-10 月恰好全为正，所以演示看不出来；真实用户一旦某月超支就会看到。

**建议**：`net_yuan` 去掉 `abs()`（`fen_to_yuan_str` 支持负数时），或前端按 `net_positive` 拼接 `-`。加一条断言：`net_fen < 0` ⇒ `net_yuan.startswith("-")`。

### 3.4 A21 接管卡"点按钮没反应"（P1，已修）

**用户报的原话（m00540）**："这个部分我点击每个按钮都没有反应"（总览「待人工接管的单」，2 张单）。

**服务端先排除了**（8123 实测）：claim / need-info / reject / cancel / resume 五条路径全部正常，状态机也拦得住非法跃迁（rejected 再 cancel → 400 HANDOFF_INVALID_STATE），不存在的单 → 400 HANDOFF_NOT_FOUND 且带人话。所以不是接口坏了。

**真正的原因（体验层，四处叠加）**：
1. 动作成功/失败**只 appendBubble 到 AI 助手页**（web/js/72-bx-core-b.js:160-237）。用户正看着总览页，卡片连"正在提交"都不显示，失败也不重渲染 → 看起来"没反应"。
2. 失败文案用浏览器原话：stale 卡 → 接管动作没成功：Failed to fetch；鉴权失败 → 旧文案教用户用 ?token=（app/api/auth.py:27-29 明确拒绝查询参数，只认 #token=，照做必然 401）。
3. needs_user 的卡（收款人有歧义）**只有操作员动作**，却写着"缺你本人的决定"，用户会去备注框写"是 4417 那个"，再点绿色「提交：取消这一轮」——把这一轮取消掉。服务端刻意不给 resume（"操作员不能替你选"），但 UI 没把这条出路指出来。
4. 计数口径同样错：共 2 张把 cancelled 也算进"待接管"，与卡片自己的"已取消"矛盾。

**已修（3 个文件，git 未提交）**：
- 卡内状态行 + 页面级 toast（.handoff-status 的 is-busy/ok/bad 三色；#bx-toast 3 秒淡出），成功与失败都就地可见；失败自动 bxCacheDrop(); bxRefresh()，并把浏览器原文换成"连不上本地服务…/鉴权没通过…/后端 user_text"。
- 备注框按动作给 placeholder + 「不填了」；needs_user 卡增加绿色「去对话里选收款人」（切页 + 预填原话 + 说明"备注框只是写给操作员的说明，不会替你选收款人"）。
- 计数改为「进行中 M 张 · 已结束 N 张（历史只作记录）」，M 与 ACTIVE_STATUSES=("pending","claimed","need_info") 一致。
- 截图：docs/交付/截图/体检/10-handoffs-fixed.png、11-handoffs-note-row.png、12-handoffs-toast.png。

**验证**：干净实例点「领取」→ 即时"正在提交…"→ 200 → 卡片变「已领取」；stale 单提交 → 400 → toast"没成功：这张接管单不存在…（正在刷新队列…）"+ 卡片消失；正常单 → 200 → 绿色 toast。check_frontend.py 91/91、pytest 1719 passed、check_docs_numbers.py 通过。

**教训（写进回归）**：任何会改状态的动作，反馈必须留在**用户当下看的那个容器**里；跨页 appendBubble 等同于没有反馈。

## 8. 消息互联互通（Q1=B 最小闭环，已落地）

> 现状：**已实现并通过回归**（后端 + 总览卡片 + 领域/接口测试 32 条，洞察 10 类）。
> 与早期设计的两处调整，都记在下面，避免"文档是设计、代码是另一套"。

### 8.1 最小闭环（实际做到的四层）

1. **事实层**：十条探测器只读账务表（`app/insights.py` + `app/insights_extra.py`，纯 SQL，**不调模型**），探不到就不说，绝不补一句"看起来很可疑"；`app/messages.py` 只留频控、落库、反馈。
2. **时机层**：每天最多 3 条（`MAX_PER_DAY=3`）、同一洞察 7 天静默（`QUIET_MS`）、同一事实靠 `dedupe_key` + `UNIQUE(user_id,dedupe_key)` 只落一条、连续 3 次"这类别再提醒"（`MUTE_AFTER_IGNORES=3`）后 `message_insight_state.muted_ms` 永久静音这一类。
3. **语言层**：句子是模板拼的，正文/标题里每个数字必须能在同一条的 `facts` 里查到——有一条单测专门扫数字 token（`tests/test_messages.py` 的 `test_every_number_in_a_message_comes_from_its_facts`）。这条规则换来的是：用户点开依据，看到的数字和正文一模一样。
4. **反馈层**：`我去处理 / 这次不用 / 这类别再提醒` 三选一，写 `message_feedback` + 翻 `messages.status`；同一动作重复提交幂等，不会把忽略次数刷成 3。

### 8.2 十条洞察（实际实现）

`app/insights.py` 的 `CATALOG` 按"先安全、后省钱"排重要度；每日封顶 3 条时，凌晨大额与同名收款人优先于省钱建议。

| ID | 触发事实 | 判据 | 一句话（示例） |
|---|---|---|---|
| I3 `I3_night_large` | 本月 00:00-05:59 单笔 ≥500 元支出 | 至少 1 笔 | "本月凌晨有 2 笔共 7,560.00 元的支出" |
| I7 `I7_payee_duplicate` | `payees` 同名但卡号尾号不同 | `COUNT(DISTINCT card_tail) > 1` | "收款人里有 2 个「张三」，尾号 4417 和 6620" |
| I5 `I5_cash_gap` | 未来 7 天预约转账 + 订阅代扣 vs 活期余额 | 两项之和 > 活期 `balance_fen` | "未来 7 天要出 1,400.00 元，卡上只有 1,260.50 元" |
| I1 `I1_subscription_hike` | 同商户本月订阅扣款 vs 上月 | `cur*10 >= prev*13`（+30%） | "爱奇艺会员这个月的扣费涨了 40%" |
| I8 `I8_budget_pace` | 预算已用比例 vs 时间已过比例 | 已用 ≥80% 且时间 ≤60% | "预算用掉 85%，这个月才过了一半" |
| I6 `I6_goal_behind` | 储蓄目标实际进度 vs 按日历应到进度 | 落后 ≥10 个百分点 | "「换电脑」存了 10%，时间已经过了 77%" |
| I4 `I4_payday_saving` | 本月最大一笔非转账/理财收入 | ≥5,000 元 | "本月进账 8,000.00 元，先存 800.00 元？" |
| I2 `I2_spending_pace` | 本月至今支出 vs 上月同期（不含转账/理财） | `cur*10 >= prev*12`（+20%） | "这个月比上月同期多花了 52%" |
| I9 `I9_idle_balance` | 活期余额 ≥10,000 元，且最近 90 天无理财类流水 | 两条都成立 | "卡上有 12,860.50 元一直没动" |
| I10 `I10_stale_handoff` | `handoffs` 里 pending/claimed/need_info 的单挂了多久 | 最老一张 ≥24 小时 | "有 1 张接管单挂了 30 小时" |

**设计取舍（为什么和早期草案不一样）**：
- 早期草案里的"疑似重复扣款"，账单页规则引擎（如 `BILL-03`）已经在异常卡里给了，再发一条等于同一件事说两遍；改成"花得比上月快"，补的是规则引擎没覆盖的**节奏**视角。
- "未来 7 天扣款 > 余额"上一轮因为要读预约/订阅并算可用余额而留到今天，现已落地成 `I5`：只比"活期余额"，**不扣 hold、不算理财赎回**，宁可在正文里写清口径，也不假装算得比自己知道的更准。
- 后补的两条（`I9`/`I10`，单独放在 `app/insights_extra.py`，因为 `insights.py` 已贴 600 行上限）：
  - `I9` 只陈述事实（余额、几天没动），**不推荐产品、不提收益**，正文固定写上「理财有风险，买不买、买什么由你决定」，避开投资建议的合规边界；动作只有 goto/问一句，没有「帮我买」。
  - `I10` 与总览「待人工接管的单」卡分工不同：卡是当下队列，提醒只说「有一张挂了多久」，且同一个月一次（`I10:{YYYY-MM}`），不会每天念一遍。
- 每条都带两个动作：`ask`（把话填进输入框，由用户决定发不发）与 `goto`（跳到账单/订阅/目标页）。**没有"帮我停掉"这类直接执行的动作**——提醒不能绕过确认卡，与验收第 9 维一致。

### 8.3 数据模型与端点（实际落地）

两张表（`app/db.py`，`TABLE_NAMES` 同步登记）：`messages`（含 `dedupe_key` 与 `UNIQUE(user_id,dedupe_key)`、`status` 闭集、`facts_json`/`actions_json`）、`message_insight_state`（`ignore_count`/`muted_ms`/`last_ms`）。反馈明细不单独立表（数据层收口时删掉了写而无读的 `message_feedback`），动作与备注直接记进 `audit_log` 的 `message.feedback`，审计链可查。

端点（`app/api/messages_api.py`，全部要 API token）：
- `GET /api/messages?limit=1..50` 只读，不生成；
- `POST /api/messages/refresh` 现在想一想（写动作，走 `app/use_cases/messages.py`，返回本轮 created/skipped + 最新列表）；
- `POST /api/messages/{id}/feedback` 反馈。

写端点一律走用例层再 `payload`，路由里没有 SQL 与事务——这是仓库对写路径的硬规矩（`tests/test_use_cases.py` 会拦）。

### 8.4 页面（总览「助手提醒」卡）

- 卡头：`今天已说 N 条 · 上限 3 条` + 「现在想一想」按钮（只有人点才会算一轮，不给自动轮询加写操作）。
- 每条：标题 + `值得核实/提示` + 状态（待你看/已采纳/已忽略）+ 正文 + **依据：facts 键值** + 动作 + 三个反馈按钮 + 时间。
- 空态明说"探不到依据就不说"，不装出"今天很健康"的假象。
- 按钮反馈留在卡片内（toast + 立即重渲染），沿用 A21 的教训：反馈不能只写进另一个页面。

### 8.5 验收对照（9 维）

| 维度 | 怎么验的 | 结果 |
|---|---|---|
| 不重复计数 | 连点两次刷新，同一事实只落一条（dedupe_key + UNIQUE） | ✅ 单测 + 浏览器 |
| 同洞察 7 天静默 | 二次 generate 返回 skipped=QUIET | ✅ 单测 |
| 忽略 3 次不再出现 | 连点「这类别再提醒」3 次后 `muted_insights` 出现该洞察 | ✅ 浏览器实测 |
| 三面同一 id 不双发 | 目前只有总览一处展示（未做消息中心），不存在双发 | ⏸ 范围外 |
| 数字与流水一致 | 数字白名单单测；facts 与正文同源 | ✅ 单测 |
| 无模型调用也能出 | 探测器纯 SQL，测试全程不 mock 模型 | ✅ |
| 降权生效 | 忽略计数落 `message_insight_state` | ✅ 单测 |
| 可关闭全部提醒 | 单条「这类别再提醒」；全局开关未做 | ⏸ 范围外 |
| 无权限提升 | 动作只有 ask/goto，没有执行类动作 | ✅ 代码审查 |

### 8.6 已知边界（下一轮再说）

- 演示种子里的订阅扣款与异常流水是"相对生成时时钟"造的，冻结到某一天跑 `refresh` 可能一条都探不到——这是种子日历的问题，不是探测器坏了（测试里用自造的确定性流水验证）。
- `score/降权排序` 未做：同一轮里三条的顺序是固定的（凌晨大额 → 涨价 → 节奏），没有按"用户更在意哪类"排序。
- 消息中心 / 助手气泡两处投递未做，目前唯一入口是总览卡（有意收敛，先看一条链路是否值得留）。
