## 3. 写端点层：34/34 都有真实 2xx，但 3 个只验到异常分支

### 3.2 信封：写统一，读不统一

- 写端点 **32/34** 走 app/api/http.py:10-18 的 `payload(outcome)` → `{"ok":true, …}`。
- 例外：`POST /api/chat` 是 text/event-stream（无 JSON 信封）；`POST /api/scheduled/{id}/verify` 是 **HTTP 200 + ok:false**（全库唯一「200 但业务失败」）。

### 3.3 四个形状级缺陷

**F1（P0，阻断）：`/api/scheduled/{id}/verify` 的成功分支经 HTTP 不可达。**
实测：两条挑战都 200 且回显 code，带 `{proofs:[{factor,challenge_id,code},…]}` 提交 →
`{ok:false, status:"needs_verification", reason:"FACTOR_NOT_VERIFIED", missing:["face","sms"], invalid:[]}`。
A/B 对照：同一组口令以 dict 直传工具层 `app.tools.scheduled.verify_and_execute(conn, id, proofs=[dict,…])` →
`{ok:true, status:"executed", result:{scheduled_id, status, amount_fen:200000}}`。
根因：app/api/plans_api.py:69 把 pydantic `FactorProof` 模型原样下传（app/api/schemas.py:250-255、app/models.py:94-101），app/security/factors.py:198-212 的 `_normalize` 只认 `isinstance(item, dict)` → 静默丢空。对照 `/api/confirm` 能过，是因为 app/api/chat_api.py:99 显式 `[item.model_dump() for item in (request.proofs or [])]`。
同构风险（复核后排除）：`BirthdayPayRequest.proofs`（app/api/schemas.py:238）在 app/api/plans_api.py:179 已经逐条 `model_dump()`，红灯生日付款走 HTTP 不会永远 waiting_factor。

**F1 已修（提交 5b00f43）**：app/api/plans_api.py:69 改为 `proofs=[item.model_dump() for item in (request.proofs or [])]`，与 /api/confirm、生日付款三处对齐；回归用例 tests/test_scheduled.py::test_verify_route_passes_plain_dicts_to_the_use_case 从路由函数这一层盯住「模型必须先转 dict」。重跑 tmp/check_writes.py 的 34 个写端点：同一条请求现在 `ok=True status=executed`（修复前 `ok=False reason=FACTOR_NOT_VERIFIED`）。

## 6. 跨层根因（为什么「都有数据」却还是对不上）

1. **没有序列化契约层**：app/api/http.py 只负责包 `ok`，不负责补 `_yuan`/`_text`。同一份「分」在 21 个字段上没有元，前端只能自己 /100（web/js/88-view-monitor.js:75）。
2. **枚举有两套半**：DB CHECK、`app/views/labels.py`、前端常量表；接口只吐 key 不吐 label，于是「waiting 显示英文」「前端 5 值 vs 4 值」反复出现。
3. **库内 JSON 直出**（F4）：`dag/failure/auth/payload` 没有子 schema，前端只能靠猜。
4. **count 是「本页条数」的旧口径**：没有升级成 total，导致安全页「待接管 N」这类显示不可信。
5. **5 个资源只有写、没有读**：提交后无法回读，等于无法自证。
