## 1. 权限分级实现说明（必填结论一）

### 1.1 规则在哪里、怎么裁决

* **规则是数据不是 if 链**：`app/policy/rules.py:222` 的 `RULES` 元组，元组顺序即优先级；`app/policy/engine.py` 的 `decide()` 直接遍历元组，**第一条命中即返回**，短路求值。
* **默认拒绝**：`R11_default_deny` 的 `when` 恒为 `True`，是兜底而不是摆设；规则表被改坏时 `decide` 抛 `AppError("RULES_BROKEN")` 而不是放行。
* **纯函数**：`decide` 不许联网、不许调模型、不许随机、不许读环境变量、不许读数据库、不许读时钟。四条都有单测守着：`tests/test_policy.py:178 test_engine_does_not_import_llm`、`:186 test_engine_does_not_read_environment`、`:194 test_engine_does_not_touch_database`、`:202 test_engine_never_calls_the_clock`；另有 `:214 test_decide_is_deterministic`（同输入必同输出）与 `:223 test_decide_does_not_mutate_context`。
* **可解释**：每条 `Decision` 都带 `rule_id` + `reason_code` + `reason_text`，`engine.explain()` 输出三行，前端右栏「策略」面板直接渲染：

```
🟡 待确认 · R06_transfer_yellow
即将转账 500.00 元给 李静
依据：单笔 500 元未超过 1000 元日累计线（今日已用 0 元）
```

### 1.5 颜色之外的第三道闸门（纵深防御）

颜色只是界面语言，真正的结构性闸门有四道，任何一道单独失效都不会导致资金落账：

1. **入口访问令牌**（`app/security/api_auth.py` + `app/api/routes.py:require_api_token`）：除 `/`、`/api/health`、`/favicon.ico` 外，所有 `/api/*` 都要求 `Authorization: Bearer` 或 `X-API-Token` 请求头（浏览器首开用 `#token=` fragment；查询参数不支持）；令牌来自 `API_TOKEN` 或 `data/api_token`（0600，首次启动 `secrets.token_urlsafe(32)` 生成），都没有则一律 401（fail closed），比较用 `hmac.compare_digest`。只挡「谁能调这个端口」，不做身份认证（无多用户/RBAC）。
2. **能力令牌七步校验**（`app/security/token.py` 的 `verify()`）：结构 → `compare_digest` 常量时间验签 → 过期 → nonce 落 `token_nonces` 表（一次性）→ tool 匹配 → `params_hash` 匹配 → `account_id`/`amount_fen` 匹配。**`CAPABILITY_SECRET` 缺失时 fail closed**（抛 `MissingCapability`），不存在「没密钥就跳过」。
3. **资金两阶段**（`app/funds.py`）：`initiate` 只写 hold 不动余额；`commit` 必须持有有效 hold 才在同一事务里扣款、写流水、写审计、写 hold 结算；`release`/`expired` 只解锁。幂等键 `sha256(session_id|node_id|params_hash)` 前 32 位保证同请求重放不重复扣款。
4. **审计只增不改**（`app/audit.py` + SQLite 触发器 `app/db.py` 的 `audit_no_update` / `audit_no_delete`）：哈希链 `sha256(prev_hash + ts + event_type + payload_json)`，`verify_chain()` 可随时复算。准确边界是「应用层只追加 + 链可验证」：触发器能挡住普通 SQL 改写，但拥有数据库文件写权限的人仍可重建整条链，不等价于对存储管理员的绝对不可篡改（残余风险见 R-04）。e2e 演示里直接 UPDATE `audit_log` 会被数据库拒绝，这是可现场验证的。

### 1.6 并发与重裁（本轮新增）

判级与账单不是同一本账：`daily_user_limits` 是按用户维度累计的**判级**依据，`daily_limits` 是账户维度的**账单视图**，两者分别写入、互不覆盖。

花钱路径的并发闸门分三层：

1. **同事务条件更新**：扣款/占额在同一个 `BEGIN IMMEDIATE` 事务里做条件 UPSERT/UPDATE，`rowcount=0` 就回滚，不靠「先查后写」。
2. **升级即重裁**：如果本笔在执行瞬间会把用户累计推过阈值，`funds` 抛 `DAILY_RISK_UPGRADE_REQUIRED`，执行器 `executor._retry_after_upgrade` 用**红灯**重判并重新索要因子，旧黄 hold 先释放；幂等键由 nonce 派生，重试不会多扣一笔。
3. **黄卡不授权红决定**：`_existing_confirmation` 校验确认卡的 `level`，用户点过的黄色确认不会被拿来放行一张红色决定。

预约转账与生日计划都走「到点重裁」：创建期的判级只作参考，真正动钱那一刻按当日最新用户累计重判（见 §1.2 的预约行、§0.2 的口径变更二）。

### 1.7 人工接管（本轮新增）

**入口是真实的**：`app/planner/runner.py` 的 `_settle` 在收款人歧义（`PAYEE_AMBIGUOUS`）或解析不到（`PAYEE_NOT_FOUND`）时不再只丢一句反问，而是把这一轮的原始请求、`run_id`、DAG、已完成节点、失败节点、失败原因与裁决/授权快照一起落成一张 `pending` 单。

**表与状态机**：`handoffs`（`run_id/session_id/user_id/account_id/status/reason/request_text/dag_json/done_nodes_json/failed_node_json/failure_json/decision_json/auth_json/operator/note/claimed_ms/created_ms/updated_ms`），状态闭集 `pending/claimed/need_info/rejected/cancelled/resumed/failed`；部分唯一索引 `idx_handoffs_active_run(run_id) WHERE status IN ('pending','claimed','need_info')` 保证同一 run 只有一张活跃单（并发建单靠它）。

**接口**：`app/api/handoffs_api.py` 暴露 8 个端点——`GET /api/handoffs`（按状态列表）、`GET /api/handoffs/{id}`、`POST /api/handoffs`（手动建单）、`POST /api/handoffs/{id}/claim`（操作员领取）、`/reject`、`/need-info`、`/cancel`、`/resume`；整组 `dependencies=[Depends(require_api_token)]`。

**并发领取**：`claim` 用条件 `UPDATE ... WHERE id = ? AND status = 'pending'`，`rowcount != 1` 返回 `HANDOFF_ALREADY_CLAIMED`（409）。两个操作员同时点只有一个赢家，另一个拿到明确错误码而不是静默覆盖。

**恢复前重查（这是「不复用过期写令牌」的落点）**：`resume` 依次检查 ①是否已有新轮次（旧 run 不再续跑）②确认卡是否存在且未过期（过期就地置 `expired` 并审计）③计划一次性授权是否仍在有效期 ④账户是否仍存在、状态可动用 ⑤余额是否仍够；任何一项不满足都不执行，按原因置 `failed` 或 `need_info`。

**不重复执行已完成节点**：恢复入口复用 `app/planner/executor.py` 的 `_drive`（`state in (done,failed,skipped)` 直接跳过），自己不写执行逻辑；即便 `executor._done` 把一个含失败节点的 run 标成结束，`resume` 仍会检查 `dag_nodes` 里是否有 failed，有就把这张单关掉并如实记失败，绝不报成功。

**失败边界**：恢复失败 → `handoffs.status='failed'`、`note` 写原因、审计 `handoff.resume_failed`。审计事件 `handoff.created/claimed/rejected/need_info/cancelled/resumed/resume_failed` 全部进 `EVENT_TYPES` 闭集（当前闭集 61 类）。

**验收测试**：`tests/test_handoff.py` **13 条**（2026-10-25 实测 `13 passed`，2.37s），覆盖 8 项验收（自动建单、重开库仍读得到 pending、并发单赢家、reject 后不可 resume、need-info 记 note、过期确认卡/授权不可 resume、不重跑已完成资金节点、每个动作有审计），外加第 13 条「用户已回答澄清 → 旧单按被取代关闭」（`executor.py:126` → `conflict.supersede_answered_clarifications` → `handoffs.close_for_run`，审计 `handoff.cancelled` 且 `closed_by=run.superseded`）。

**如实边界**：operator 不是身份只是审计字符串；无 RBAC、无工单分派、无通知、无 Web 操作台；不对接真实坐席系统。**关单路径**：用户回答澄清后旧 pending 单会被自动收掉（见上条，审计 `handoff.cancelled` / `closed_by=run.superseded`）；**仍缺**「用户既不作答也不取消」时的超时或巡检关单——这种单会一直挂在队列里，只能靠操作员 `cancel`。

### 1.8 沙箱：能做与不能做的宣称（本轮新增）

本节只写可复跑的事实，完整说明在 `docs/security_sandbox.md`。

- **架构选择是「消除执行面」**：主 Agent 不执行任意模型生成代码，所有动作都是白名单工具函数；仓库内没有 `eval/exec` 调用链可以逃逸。
- **实测**：`scripts/prove_no_exec_surface.py` 扫 **75 文件 / 25383 行**，代码执行面 **0 命中**；出网仅 **3 处**（`app/llm.py:7`、`:297`、`:303`，都是模型供应商）；动态 SQL **13 处**全部人工复核；离线 `subprocess` **9 处**只在测试/脚本侧。
- **不能宣称的**：这不是已部署的容器沙箱，没有 seccomp/只读根文件系统/出网白名单；API 进程、SQLite 与模型调用同机同用户，拿到 shell 或数据库文件写权限的人可绕过应用层所有控制。
- **剩余风险**：见 R-22；后续在部署层补容器 + 只读根 + seccomp + 出网白名单。

### 3.4 结论（不粉饰版）

1. **结构性安全是成立的**：令牌、幂等、两阶段资金、审计链、默认拒绝五道机制在 43 条对抗用例下**没有出现过一次资金损失、令牌绕过或信息泄露**。
2. **语义级安全仍有欠账**：14 条用例未全数达标 —— 全部是级别不达标（13 条停在 `level=none`：B03/B06/B07/B08、C01/C02/C08/C10、D04、D05、E01/E02/E05；1 条判成 green：D02），其中 3 条同时审计不齐（C08、D04、D05）。按赛题评审口径「被拦」必须体现在策略裁决上，因此这 14 条**计入未拦截**，已全部登记在 §2.2 与 §2.1 的 R-05/R-07/R-08/R-09/R-12。
3. **优先修复顺序**：① R-08 意图层补齐与短路留痕（改动最大，直接决定 8 条用例的达标率）；② R-05 命中后升色口径 + 反问轮扫描（影响 D02/D04/D05，原计划的注入升级任务已作废，见 `docs/技术文档.md §7 R14`）；③ R-07 剩余 3 条审计缺项（C08、D04、D05）。
