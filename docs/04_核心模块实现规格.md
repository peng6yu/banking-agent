# 04 核心模块实现规格（逐函数分支表）

> 本章的每个函数都必须按分支表实现。分支表里没写的情况**不要自己补**，按「默认拒绝 / 抛错」处理，然后写进 `docs/QUESTIONS.md`。

## 4.1 clock.py —— 统一时间源

```python
def now_ms() -> int          # 当前 Unix 毫秒
```

| 条件 | 行为 |
|---|---|

## 4.2 errors.py —— 异常层级

```
AppError
├─ ValidationError      输入不合法
├─ MissingCapability    执行缺 token          → HTTP 403
├─ TokenExpired         令牌过期             → HTTP 403
├─ TokenMismatch        令牌与参数不匹配     → HTTP 403
├─ PolicyDenied         策略拒绝             → HTTP 403
├─ InsufficientFunds    余额不足             → HTTP 409
├─ HoldExpired          冻结已过期           → HTTP 409
├─ InjectionDetected    注入命中             → HTTP 400
└─ BreakerOpen          熔断中               → HTTP 429
```

| 规则 | 说明 |
|---|---|
| 每个异常带 `code: str` 与 `user_text: str` | `user_text` 是给用户看的中国话，不含技术细节 |
| 禁止 `except Exception` 后静默 | 必须 `raise` 或转成上述之一 |
| API 层统一映射 | 见 07 章的分支表 |

## 4.3 money.py —— 金额

```python
def to_fen(yuan: float | int | str) -> int
def fmt_yuan(fen: int) -> str            # 1286050 -> '12,860.50'
def parse_amount(text: str) -> int       # 自然语言 -> 分
```

### `to_fen` 分支表

| 输入 | 行为 |
|---|---|
| int / 纯整数 str | 乘 100，返回 int |
| 小数 str | `Decimal(s)` 后乘 100，**必须整数**，否则抛 `ValidationError('精度超过分')` |
| float | 先 `Decimal(str(x))`，同上 |
| 负数 | 抛 `ValidationError('金额必须为正')` |
| 0 | 抛 `ValidationError('金额必须大于 0')` |
| > 100 万元 | 抛 `ValidationError('单笔超过 100 万元')` |

### `parse_amount` 分支表（中文口语必须支持）

| 输入样例 | 返回（分） | 依据 |
|---|---|---|
| `500` / `五百` / `500块` / `500元` | 50000 | 阿拉伯或中文数字 |
| `五百五` | 55000 | 口语省略单位「十」→ 十位 |
| `一千二` | 120000 | 省略单位「百」→ 百位 |
| `500.5` / `五百五毛` | 50050 | 角 |
| `两块五` | 250 | 口语小金额 |
| `全部` / `所有钱` | 特殊值 `-1` | 由调用方替换成余额，**不允许在 money 里查库** |
| 空串 / 无法识别 | 抛 `ValidationError('没听懂金额')` | — |

实现建议：先用正则抓阿拉伯数字与单位，再对纯中文走一张字符映射表 `{零:0,一:1,...,十:10,百:100,千:1000,万:10000}`，按位累加。**不要引入 `cn2an` 之类外部依赖**，20 行能写完，且行为可控。

### `fmt_yuan` 分支表

| 条件 | 行为 |
|---|---|
| fen 为负 | 前置负号 |
| 小数部分为 0 | 仍保留 `.00`（银行界面惯例） |
| 千分位 | 必须加逗号 |

```python
def connect(path: str | None = None) -> sqlite3.Connection
```

### `tx` 分支表

| 条件 | 行为 |
|---|---|
| 当前无事务 | `BEGIN IMMEDIATE` … 成功 `COMMIT`，异常 `ROLLBACK` |
| 已在事务中 | 用 `SAVEPOINT`，只回滚本段（嵌套安全） |
| 异常 | 回滚后原样抛出，**不许吞** |

### `sweep_expired_holds` 分支表

| 条件 | 行为 |
|---|---|
| `status='held'` 且 `expires_ms < now` | 改 `expired`，写 `transfer.released` 审计 |
| 否则 | 跳过 |
| 返回 | 处理条数（0 也算正常） |

启动时调一次，之后每 30 秒一次（`main.py` 里起 `asyncio` 任务）。

## 4.9 2026-10-23 新增契约（拒答守卫 / SystemBusy / 注入下限 / 认领严格化 / 降级链）

这一节记录红队收口时新增或收紧的契约，写新代码时按这里的口径来，别照旧文档反着改。

### 4.9.1 `app/planner/refusal.py`：确定性拒答守卫（模型之前的一道闸）

| 约束 | 说明 |
|---|---|
| 位置 | `intent.parse()` 的**第一件事**，早于任何模型调用 |
| 命中后的返回 | `IntentResult(intent="unsupported", slots={refusal: <话术>, refusal_category: <类别>}, confidence=0.99, ok=True, source="guard")` |
| 下游 | `planner_dag.build_or_single` 走 `unsupported_request` 哨兵图，R03 判红；`app/policy/rules.py` 的 `_emit_unknown_tool` 优先用 `params["refusal"]` 当 `reason_text`，没有才用默认「我还不会这个操作」 |
| 审计口径 | 仍是 `R03_unknown_tool` / `UNKNOWN_TOOL`，不新增规则号——它本来就是"请求了一个系统不具备的能力" |
| 纯函数 | 只 import `re` / `dataclass`，第 4 层，无网络无模型；单测用"被调用就抛错"的适配器证明它确实在模型之前返回 |
| 不压棒 | 命中守卫的那一轮**只扫注入、不写污点棒**（`_scan_only`），免得把用户的正当话术变成下一轮的污点 |

八类判定（每类都是"两个词同时出现"，宁漏不误伤）：验证码索取、系统提示词索取、密钥索取、删审计/流水、加收款人、改登录密码、读登录密码、冒充内部身份查他人资料。

### 4.9.2 `SystemBusy`：写锁竞争不再落 INTERNAL

- `app/clock.py` 新增 `class SystemBusy(BankError)`：`code="SYSTEM_BUSY"`、`http_status=503`、`user_text="系统正忙，刚才这笔没有执行，过一会儿再试一次。"`。
- `app/db.py` 的 `as_busy_error(exc)` 把 `sqlite3.OperationalError` 里的 `database is locked` 等四种 marker 转成 `SystemBusy`，其它异常返回 `None`。
- `executor.run` 在原来的 `BankError` 分支之后加了一层 `except Exception`：能转就转（记 `executor.run.busy` 日志 + `error` 事件），转不了才往上抛。
- 口径：以前写锁没抢到会一路冒到 `routes._start_run` 的兜底，落 `INTERNAL`——分不清"系统忙"还是"代码有 bug"。现在用户看到的是人话，审计里能区分。

### 4.9.3 注入下限：`IntentResult.injection_level_floor` 与反问轮留痕

| 字段 / 行为 | 说明 |
|---|---|
| `IntentResult.injection_level_floor` | `"green"|"yellow"|"red"`，取自 `injection.level_floor_for(patterns)`（资金转移类与密钥类命中为 red，其它注入命中为 yellow） |
| 反问轮（`ok=False`） | **也扫注入**，但不压棒、不建 DAG；categories 与 level_floor 记在结果里，给上层留痕 |
| `routes._audit_injection_reflection` | 反问轮与守卫轮补写一条 `injection.detected`：payload 固定 `{source:"user_text", fields:[], categories, escalated:false, level_floor, reflection:true}`；执行轮不重复记（`fields` 为空表示"命中的是用户原话，不是某个槽位字段"） |

### 4.9.4 污点棒认领：严格相等（2026-10-23 收紧）

- `injection.claim_turn(session_id)` 只领 `session_id` **完全相同**的棒；`session_id=None` 的调用方只领匿名棒；领不到返回 `None`。
- **删掉了"有会话号就去领匿名棒"的兜底**：它会让 B 会话领走 A 会话留下的匿名污点，造成跨会话串味。宁可漏升色（少一次升色），也不误升色（把别人的话算到你头上）。
- 生产链路 `intent.parse` 一定带 `session_id`（`intent.py` 的 `mark_turn(text, session_id=session_id)`），匿名棒只可能来自离线脚本/单测。

### 4.9.5 写库失败的降级审计与 `trace_id`

- 审计写库抛异常时，把整行 JSON 追加到 `data/audit_fallback.log`（可用 `AUDIT_FALLBACK_PATH` 覆盖路径）：`{ts_ms, trace_id, session_id, event_type, degraded:true, reason, payload}`，只 `log.exception` 不外抛。
- 回包带 `trace_id=new_id("tr")`（`app/ids.py` 白名单已加 `tr`），用户可以拿它回查落盘记录；**不假装成功**，该 `INTERNAL` 还是 `INTERNAL`。
- `run.failed` 的 payload 只写 `error_type` 与 `node_tool`，**不写异常原文**，避免把敏感数据带进日志。

### 4.9.6 模型降级链（`app/config.py` / `app/llm.py`）

| 项 | 约定 |
|---|---|
| 配置 | `LLM_FALLBACK`（同厂商模型名，逗号分隔）与 `LLM_FALLBACK_VENDORS`（`base_url::模型名::KEY_ENV_NAME`，第三段是**环境变量名**，配置串里绝不出现密钥） |

### 4.10 澄清上下文与确认窗口（2026-10-23 收口「已知限制」时新增）

#### 4.10.1 `app/planner/clarify.py`：反问轮把短回答接回原话

| 约束 | 说明 |
|---|---|
| 层号 | 第 4 层（纯内存 + `app.clock`），无网络无模型无库；`tests/test_imports.py` 里 `ALLOWED = {app.clock}` |
| 写入口 | `runner._settle` 在 `question is not None` 分支里 `remember(session_id, text=state.user_text, query=<原查询>, candidates, question)` |
| 读入口 | `routes.chat()` 先 `augment(session_id, request.text)`：命中就返回「原话（收款人卡尾号4417）」当本轮解析文本，否则返回 `None` 并用用户原话；未接上时 `forget(session_id)` |
| 只认候选里真实存在的东西 | 尾号必须等于某个候选的 `card_tail`；序号 1-based 必须落在候选取值范围内。手滑填一个不存在的尾号不会被当成选择 |
| 尾号正则 | `(?:尾号|后四位|末四位|卡号)?\s*(\d{4})(?!\d)` —— 允许裸 4 位，但前后不能再接数字 |
| 序号正则 | `第\s*([一二三四五六七八九十]|\d{1,2})\s*(?:个|位|张|条)` |
| 生命周期 | `CLARIFY_TTL_MS = 300_000`（5 分钟）；命中即 `forget`（用一次就忘）；换话题/未命中也在路由层清掉 |
| 兜底不变量 | 接不上的短回答一律按原话走原有反问逻辑——**不猜人**，宁可再问一次 |

#### 4.10.2 确认窗口可配（`app/planner/state.py`）

- `confirm_timeout_ms()` 读 `CONFIRM_TIMEOUT_S`：空 → `CONFIRM_TIMEOUT_MS`（120000）；非整数、`< MIN_CONFIRM_TIMEOUT_S`(10)、`> MAX_CONFIRM_TIMEOUT_S`(3600) → 回落 120000 并 `log.warn("planner.confirm_timeout.invalid" / `.out_of_range`)`。
- 三处必须同档：`state.new_confirmation` 的 `expires_ms`、`executor.run(confirm_timeout_ms=...)` 的等待时长、`events.prompt_payload` 的 `expires_in_s`。**别在任一处硬编码 120**。
- 理由：120 秒是演示取的值，不是业务常量；窗口长度属于部署参数，改了不该动代码。
