## 一、修复方向（四问逐条回答）

### 1. `schedule_transfer` 是否移出 `CONFIRM_ONLY_TOOLS` 并进入 `SPEND_TOOLS`
**是。** `app/policy/rules.py:31` 的 `SPEND_TOOLS` 现为 `{transfer, reserve_funds, pay_merchant, split_transfer, schedule_transfer}`；`CONFIRM_ONLY_TOOLS`（rules.py:36）只剩 `{cancel_subscription, apply_virtual_card, cancel_scheduled}`。严重缺陷 B 已消除。

### 2. 日线豁免有没有连带放宽单笔上限
**没有。** `_DAILY_RULE_EXEMPT_TOOLS`（rules.py:40）只含 `schedule_transfer`，且只被 R07 引用（rules.py:315 的条件里 `action.tool not in _DAILY_RULE_EXEMPT_TOOLS`）。R08 单笔上限（rules.py:322）没有任何豁免分支。

实跑核对（直接调 `app/policy/engine.decide`）：

```
schedule_transfer  amount=  99999 -> yellow R06_transfer_yellow      factors=[]
schedule_transfer  amount= 100000 -> yellow R06_transfer_yellow      factors=[]
schedule_transfer  amount= 100001 -> red    R08_transfer_red_single  factors=['face','sms']
schedule_transfer  amount= 200000 -> red    R08_transfer_red_single  factors=['face','sms']
```

与 `transfer` 的对照结果逐行一致——**同样金额的预约与当面转账现在风险等级相同**，这正是 t11 要修的缺陷 B。

### 3. 到点自签令牌的等级会不会退化成硬编码
**不会。** `app/tools/scheduled.py:241` 写的是 `level="red" if verified else "yellow"`，其中 `verified = int(row["factor_verified_ms"] or 0) > 0`；而 `factor_verified_ms` 只在创建期 `payload.level == "red"` 时写入（scheduled.py:101），`payload` 来自 `token_mod.verify`，是 HMAC 验签过的策略裁决结果。要让 `verified` 为真，必须持有一枚策略层判红并集齐 `face+sms` 后才签发的令牌。硬编码 yellow 的路径已不存在。

补充确认：到点执行处在 `try` 内、任何异常都会把该行置 `failed` 并留 `log.warning`（scheduled.py:281-288），不会静默跳过。

### 4. 顺延是否会死循环
**不会。** `_defer`（scheduled.py:297 起）每轮 `count = int(row["defer_count"] or 0) + 1`，且先判 `count > MAX_DEFERRALS`（scheduled.py:52，值为 7）才落 `failed`；`new_due = _next_day_ms(old_due)` 用墙上时间折回（scheduled.py:304），跨夏令时不漂。因为新 `due_ms` 恒大于当前 `stamp`，同一次 `execute_due` 的 `due_ms <= ?` 查询不会重复捞到同一行。超过 7 次后行为：置 `failed` 并写 `scheduled.deferred{gave_up:true}` 审计。

## 四、findings

### F1（medium，功能缺陷 / fails closed）预约转账在「今日已花接近额度」时被 R11 默认拒绝

**位置**：`app/policy/rules.py:298-309`（R06 条件含 `not _over_daily(action, ctx)`）与 `app/policy/rules.py:315`（R07 排除 `schedule_transfer`）二者的组合。

**复现**：

```
>>> decide(Action(tool='schedule_transfer', params={'amount_fen':50000}, account_id='a1', amount_fen=50000),
           PolicyContext(spent_today_fen=90000))
level=red  rule=R11_default_deny  factors=[]
```

**原因**：今日已花 900 元时排一笔 500 元预约——
- R06 要求 `not _over_daily`，而 900+500=1400 > 1000，不匹配；
- R07 按 t11 的设计排除了 `schedule_transfer`（日线归出账那天判），也不匹配；
- R08 只判单笔，500 ≤ 1000，不匹配；
- 于是掉到 R11 `DEFAULT_DENY`（rules.py:343-346，`when` 恒为真）→ **red 且 `required_factors=[]`**。

**用户可见后果**：`executor._blocked`（executor.py:390）对「红且无因子」的处理是直接告知并终止、不给执行出口，用户看到的是 R11 的文案「这个操作我不确定是否安全，先不做」。也就是说，**排一笔 500 元的预约会被无理由拒绝**，而它的钱要到明天才出账，创建当天根本不该受当日额度约束。按 docs/05 5.x 的设计本意，这种情况应当是黄灯确认。

**为什么算缺陷而不是取舍**：R11 的语义是「未知工具默认拒绝」，而 `schedule_transfer` 是已知的、有自己的规则族（R06/R08）的工具。让一个已知工具因为规则组合的空隙掉进兜底拒绝，会同时造成两个后果：① 用户被拒绝且理由文案与真实原因无关；② 审计里这次拒绝会记成 `DEFAULT_DENY`，事后归因时会被误读成「模型调了未知工具」。

**安全影响**：无。判红并拒绝是 fail closed，不会让钱多转出去。因此定级 medium 而非 blocker。

**requiredFix**：让 R06 的日线前置条件同样尊重 `_DAILY_RULE_EXEMPT_TOOLS`（即 `schedule_transfer` 在创建期只看单笔上限、不看当日累计），并在 `tests/` 增加两条回归：① 今日已花 900 元 + 预约 500 元 → yellow/R06；② 今日已花 900 元 + 预约 2000 元 → 仍必须 red/R08 且带 face+sms（确认放宽 R06 没有连带放宽单笔上限）。

**覆盖率佐证**：`grep -rn 'spent_today_fen' tests/` 共 9 处命中，**没有任何一处**把 `schedule_transfer` 与 `spent_today_fen` 放在一起测过。这正是这条空隙能活到终审的原因。
